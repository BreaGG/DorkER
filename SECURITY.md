# Security Policy

## Purpose

This document outlines the security policy for the DorkERproject.  
Its goal is to define responsible practices for reporting vulnerabilities, handling security-related issues, and ensuring that the project is maintained in a safe and trustworthy manner.

DorkERis an OSINT-focused tool and must be used in a lawful, ethical, and compliant way.  
No functionality in this project is designed to exploit, attack, or compromise systems.

---

## Supported Versions

Security updates will be provided on a best-effort basis for the latest version of the project.  
Older versions may not receive patches unless the vulnerability is critical and easy to address.

```

| Version | Supported          |
| ------- | ------------------ |
| Latest  | Yes                |
| Older   | Case-by-case basis |

```

---

## Responsible Use

Users must ensure:

- They have proper authorization before performing any form of digital reconnaissance.
- They comply with all applicable laws and regulations.
- They use the tool strictly for legal OSINT, cybersecurity research, training, or personal learning.
- They avoid targeting systems, individuals, or organizations without explicit permission.

The maintainer is not responsible for misuse or unlawful activity conducted using this project.

---

## Reporting a Vulnerability

If you discover a security vulnerability in the project, you are encouraged to disclose it responsibly.

To report a vulnerability:

1. Do **not** open a public GitHub Issue describing the vulnerability in detail.
2. Instead, contact the project maintainer directly.

**Maintainer:** Alejandro Brea Gascón  
**Reporting Method:** GitHub private message or by opening a GitHub Issue titled "Security Disclosure" without including sensitive details.

Once contacted, you will be asked to provide:

- A clear description of the vulnerability.
- Steps to reproduce.
- Potential impact.
- Suggested remediation if applicable.

You will receive a confirmation within a reasonable timeframe.

---

## Handling of Reports

Once a vulnerability is reported:

1. The maintainer will investigate the issue.
2. If confirmed, a patch or fix will be prepared.
3. Depending on severity, a security release may be issued.
4. If required, a security advisory will be published.

The reporter may be acknowledged (with permission) in the release notes or kept anonymous.

---

## Security Best Practices for Contributors

If contributing to the project, please ensure:

- No sensitive data, credentials, or private information is committed.
- Logs, caches, or evidence folders are excluded via `.gitignore`.
- New features follow ethical OSINT principles.
- Dependencies are kept updated to avoid exposing the project to known vulnerabilities.
- No code is added that performs intrusive or unauthorized actions.
